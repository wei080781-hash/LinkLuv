# LinkLuv 專案：資料與媒體快取功能說明書

本文件定義系統如何處理不同資源的快取，以實現高效能的使用者體驗。本專案採用 **雙層快取架構**：文字資料採用「伺服器端記憶體快取」，媒體檔案則採用「瀏覽器端硬碟快取」。

## 1. 架構概覽表

| 資源類型 | 快取層級 | 儲存位置 | 關鍵設定/檔案 |
| :--- | :--- | :--- | :--- |
| **留言文字** | 伺服器端 (Server) | Redis (記憶體) | `MessageController.php` |
| **圖片/影片** | 用戶端 (Browser) | 瀏覽器磁碟快取 | `public/.htaccess` |

---

## 2. 詳細運作與測試路徑

### A. 留言文字快取 (文字資料)
*   **目標**：避免重複存取資料庫 (Database)，提升留言牆載入速度。
*   **運作機制**：
    *   系統將留言牆資料 (JSON) 儲存於 Redis 記憶體中，預設效期 60 分鐘。
    *   當執行「新增、刪除、編輯」留言時，系統強制清除相關快取 (`Cache::forget`)。
*   **測試驗證點**：
    1.  **資料同步**：發送一則新留言後，重新整理頁面，應**即時**看到新留言（代表快取已成功清除並重新載入）。
    2.  **效能觀察**：查看伺服器 Log 或使用 Debug 工具，觀察 `GET /api/messages` 的請求，若 Redis 工作正常，資料庫查詢次數應顯著降低。

### B. 多媒體檔案快取 (圖片與影片)
*   **目標**：降低伺服器頻寬消耗，實現檔案「秒開」體驗。
*   **運作機制**：
    *   透過 `.htaccess` 設定 `Cache-Control` 標頭，告知瀏覽器檔案過期時間為「一年」。
    *   檔案儲存於 S3 (圖片) 或本機硬碟 (影片)，當瀏覽器請求後，檔案會存入瀏覽器的 Disk Cache。
*   **測試驗證點**：
    1.  **打開 Chrome 開發者工具 (F12)** -> **Network (網路)** 頁籤。
    2.  點擊某個影片或圖片請求，查看 **Headers**：
        *   確認是否存在 `Cache-Control: max-age=31536000` (一年)。
    3.  **驗證快取命中**：重新整理頁面後，查看 Network 頁籤中的 **Size** 欄位：
        *   若顯示 `(from disk cache)`，代表快取功能測試通過，請求未經網路傳輸。

## 3. 特殊處理：影片轉碼管線 (Media Pipeline)

此部分非「快取」，而是「效能優化處理」。

*   **流程**：`Client上傳` -> `本機硬碟暫存` -> `CompressVideoJob (背景轉碼)` -> `上傳至 S3` -> `刪除本機原始檔`。
*   **測試驗證點**：
    1.  **背景任務**：上傳影片後，檢查終端機 `php artisan queue:work` 輸出，應看到 `CompressVideoJob` 正在執行。
    2.  **狀態更新**：檢查資料庫 `messages` 表，上傳初期 `status` 應為 `processing`，轉碼完成後應變更為 `ready`。
    3.  **資源清理**：確認影片轉碼完成並上傳 S3 後，伺服器本地 `storage/app/public/videos/` 目錄內不應長期殘留原始影片檔。

## 測試人員檢查清單 (Checklist)

- [ ] **[文字]** 新增留言後，留言牆是否立即更新？(檢查 Redis 是否成功清除)
- [ ] **[媒體]** 在 Chrome F12 開發者工具中，首次載入圖片/影片是否顯示 `200 OK`？
- [ ] **[媒體]** 重新整理頁面後，該圖片/影片請求是否顯示 `(from disk cache)`？
- [ ] **[影片]** 上傳影片後，檢查背景佇列是否正常啟動 `CompressVideoJob`？
- [ ] **[影片]** 轉碼完成後，確認影片能否正常播放且畫質是否被壓縮至合理範圍？
